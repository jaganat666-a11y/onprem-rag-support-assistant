# Слои стенда: запуск и устройство

Русский · [English](operations.en.md)

Как поднять каждый слой и что у него внутри. Окружение — WSL2 (Ubuntu) и
Docker; видеокарта нужна только серверу модели, остальное работает на CPU.

## Запуск

Весь стенд одной командой. Первый запуск собирает образ фасада и скачивает
модели (Qwen ~5 ГБ для vLLM, bge-m3 и реранкер для фасада) — несколько минут.

```bash
docker compose --profile gpu up -d   # vLLM :8000, фасад :8080, PostgreSQL :5432,
                                     # Grafana :3000 (admin / см. .env.example),
                                     # Prometheus :9090, Loki :3100
```

Сервисы, которым нужна видеокарта NVIDIA (`vllm`, `gpu-exporter`), вынесены в
профиль `gpu`. Без профиля поднимается только CPU-часть — так стенд запускается
и на машине без GPU, а фасад отвечает 503 «degraded»:

```bash
docker compose up -d                                   # всё, кроме vllm и gpu-exporter
docker compose up -d prometheus grafana node-exporter  # только мониторинг, без сборки фасада
```

Дашборды Grafana подхватываются автоматически из `monitoring/grafana/provisioning/`.

## Сервер модели (vLLM)

Сервис `vllm`: образ `vllm/vllm-openai:v0.23.0` (версия закреплена — на ней
снята оценка), Qwen2.5-7B-Instruct-AWQ под именем `qwen2.5-7b`, контекст 8192
токена, 85% видеопамяти. Фасад обращается к нему по имени сервиса
(`VLLM_BASE=http://vllm:8000/v1`), Prometheus — к `vllm:8000/metrics`.

- Веса лежат на хосте в `~/vllm-hf-cache` (другой путь — `VLLM_HF_CACHE` в
  `.env`) и не скачиваются заново при пересоздании контейнера.
- Готовность: healthcheck на `/health` с `start_period: 300s` — модель грузится
  2–3 минуты, до этого контейнер в статусе `starting`.
- Восстановление: `restart: unless-stopped` — после краша или перезапуска
  Docker vLLM поднимается сам.
- У фасада нет `depends_on: vllm`: он стартует и без модели, а `/health`
  показывает, что генерация недоступна.

```bash
docker compose --profile gpu up -d vllm      # поднять или пересоздать только vLLM
docker compose logs -f vllm                  # загрузка модели, ошибки CUDA/OOM
docker inspect -f '{{.State.Health.Status}}' vllm   # starting → healthy
curl http://localhost:8000/v1/chat/completions -H 'Content-Type: application/json' \
  -d '{"model":"qwen2.5-7b","messages":[{"role":"user","content":"ping"}]}'
```

## Путь вопроса (rag/rag.py)

1. Эмбеддинг вопроса **bge-m3** (текст → вектор для поиска по смыслу) и
   косинусный поиск 12 кандидатов среди фрагментов runbook'ов
   (`corpus/runbooks/`).
2. Реранк — пересортировка кандидатов кросс-энкодером **bge-reranker-v2-m3**: он
   читает вопрос и фрагмент вместе и ставит балл близости. Эмбеддер и реранкер
   работают на CPU — видеокарта занята моделью.
3. Порог уверенности: если балл лучшего фрагмента ниже `RAG_MIN_SCORE=0.3`,
   модель не вызывается. Ответ — «уверенного ответа в runbook'ах нет» и три
   ближайших runbook'а, вопрос помечается для дежурного (`escalate`).
4. Контекст: до двух runbook'ов (`RAG_CTX_RUNBOOKS=2`), чей лучший фрагмент не
   ниже порога, целиком и в порядке документа. `RAG_CTX_RUNBOOKS=0` — прежний
   режим, 8 фрагментов в порядке реранка.
5. Генерация в vLLM, температура 0.
6. Строка «Источник» — runbook, найденный первым; её ставит код, а не модель.
7. Сторож команд: строки кода, которых нет в контексте, перечисляются под
   блоком с пометкой ⚠️. Пропущенные шаги и предупреждения он не ловит.

Почему устроено именно так — в [eval.md](eval.md). Индекс кешируется на диск и
пересчитывается при изменении runbook'ов: холодная индексация ~60 с, тёплая —
мгновенно.

```bash
pip install -r rag/requirements.txt
py rag/rag.py "Контейнер vLLM упал с OOM — как диагностировать и что сделать?"
```

## API-фасад (facade/app.py)

Тонкий FastAPI-слой над `rag/rag.py`: логику поиска он не дублирует, а
импортирует.

- `POST /ask` `{"question": "..."}` — ответ и служебные поля:

  | Поле | Что в нём |
  |---|---|
  | `answer` | текст ответа со строкой «Источник» и пометками ⚠️ |
  | `sources` | runbook'и, ушедшие в контекст |
  | `cited` | runbook, названный источником |
  | `unverified` | число строк команд, помеченных сторожем |
  | `escalate` | `true`, если модель не вызывалась и вопрос передан дежурному |
  | `retrieval_s`, `latency_s` | время поиска на CPU и генерации в vLLM; полное время — их сумма (поиск ~16 с) |
  | `completion_tokens`, `ask_id` | токены ответа и номер строки в журнале |

  Если vLLM недоступен — `502 {"detail": "Upstream vLLM unreachable: ..."}`.
- `POST /feedback` `{"ask_id": 42, "rating": 1 | -1, "comment": "..."}` — оценка
  👍/👎 ложится в ту же строку журнала. `404` — нет такого успешного ответа,
  `503` — журнал недоступен.
- `GET /health` — `200`, если индекс загружен и vLLM отвечает; иначе `503`.
- `GET /` — демо-чат (`facade/demo.html`, один HTML без внешних зависимостей):
  вопрос, ответ с источником, жёлтая плашка при эскалации, 👍/👎. Своей логики
  у страницы нет — она ходит в те же `/ask`, `/feedback` и `/health`.

Локальный запуск на хосте (vLLM уже слушает :8000; адрес — `VLLM_BASE`, по
умолчанию `http://localhost:8000/v1`):

```bash
pip install -r facade/requirements.txt
py -m uvicorn facade.app:app --port 8080       # прогрев индекса ~10–70 с на CPU
curl http://localhost:8080/health
curl -X POST http://localhost:8080/ask -H 'Content-Type: application/json' \
  -d '{"question":"Контейнер vLLM упал с OOM — как диагностировать?"}'
```

## Логи (Loki + Promtail)

Promtail читает stdout контейнера фасада через Docker-сокет и отправляет в Loki
с меткой `job="facade"`. Весь поток — JSON (`ts`, `level`, `logger`, `msg` и
контекст запроса): access-логи uvicorn выключены, строку на каждый запрос пишет
само приложение, прогресс-бары загрузки моделей погашены. Одна строка лога —
один валидный JSON, и фильтр по полям работает без сбоев.

```bash
docker compose up -d loki promtail        # Loki :3100, Promtail тянет логи фасада
```

В Grafana — дашборд **Facade Logs (Loki)**: частота ошибок и живой поток логов.
Ошибки фасада — фильтром по полю, а не по подстроке `|= "error"`:

```logql
{job="facade"} | json | level="ERROR" | line_format "{{.ts}} {{.level}} {{.msg}}"
```

Loki, а не ELK: на одном узле Loki легче — он индексирует только метки (`job`,
`level`), а не весь текст, и показывается в той же Grafana, что и метрики.
Полнотекстовый поиск Elasticsearch оправдан на больших объёмах, здесь он
избыточен.

## Журнал запросов (PostgreSQL)

Каждый обработанный `/ask` фасад пишет строкой в таблицу `ask_log`: время,
вопрос, статус, время ответа, токены, источники, эскалация, оценка. Журнал
вспомогательный: если PostgreSQL лежит, `/ask` продолжает отвечать. Запросы
дежурного, миграции и проверка устойчивости — [sql.md](sql.md).
