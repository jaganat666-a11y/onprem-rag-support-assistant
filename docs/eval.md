# Оценка качества ответов

Как проверяется, что ассистент отвечает правильно: фиксированный набор
вопросов, метрики поиска отдельно от метрик ответа, два судьи-модели вслепую и
проверка команд скриптом. Код — [eval/](../eval/), сырые ответы и отчёты —
[eval/runs/](../eval/runs/), там же оглавление прогонов.

## Итоги на 01.10.2026

Стенд: Qwen2.5-7B-Instruct-AWQ на видеокарте 8 ГБ, поиск по 12 кандидатам с
реранком, порог уверенности 0,3, в контекст — до двух runbook'ов целиком,
температура 0, сторож команд.

Тот же поиск, контекст и промпт — ответ пишет другая модель:

Выводы:

1. **Поиск справляется, узкое место — генерация.** Корпус выдуманный, ответов
   заранее не знает ни одна модель. Раз Sonnet на том же контексте верен в
   39–40 вопросах из 40, нужные факты в контекст попадают. Qwen2.5-7B — то, что
   помещается на vLLM в 8 ГБ вместе с KV-кешем (модели 9B уже не влезли);
   выше цифру поднимет только модель другого класса.
2. **Выдуманную команду видно, пропуск — нет.** Сторож помечает каждую строку
   кода, которой нет в runbook'ах. Пропущенный шаг или предупреждение («только
   L2», «сначала проверить статус у банка») ловят только судьи. Единственный
   неверный ответ (q06) именно такой: совет оформить возврат денег, который
   RB-02 запрещает.
3. **Короткие вопросы упираются в порог.** Нужный документ поиск находит, но
   балл уверенности у короткого вопроса низкий, и 8 из 10 уходят дежурному с
   подсказкой вместо ответа. Абсолютный порог на таких вопросах не работает.

Ограничения:

- Набор вопросов писал автор корпуса, формулировки близки к тексту runbook'ов.
  Отложенный набор коротких вопросов показал, что на них поиск слабее.
- Корпус маленький: 16 runbook'ов, 96 фрагментов. Восемь случайных фрагментов
  попали бы в нужный runbook в 42% вопросов, первый случайный — в 6%. На
  сотнях документов поиск нужно мерить заново.
- На 40 вопросах доля верных около 80% известна с точностью около ±12 п.п.
  (95-процентный доверительный интервал), доля около 65% — с точностью ±15 п.п. Разница меньше ~10 п.п. — не находка.
- Оба судьи — Claude, Sonnet оценивал и свои ответы. Судьи видели пометки ⚠️:
  без пометок у 7B — 30 / 25 верных. Ручная сверка судьи — 10 ответов, и
  отметки ставились с видом его вердикта.
- У 7B температура 0, как в фасаде; у GigaChat и Sonnet — по умолчанию их API.
  Каждая строка — один прогон, разброс ±1–2 ответа.
- Провалы разбирались на том же наборе, на котором мерились. Правки общие, не
  под конкретные вопросы, но отдельного набора с судьёй для них нет.
- Локальные модели новее 7B не проверены: Qwen3.5-9B и GigaChat 3.1 Lightning в
  сборках для vLLM в 8 ГБ не помещаются, нужен другой сервер инференса
  (llama.cpp и GGUF).
- Время зависит от железа: поиск идёт на CPU ноутбука (Ryzen 7 6800H, 8 ядер),
  генерация — на RTX 3070 Ti Laptop 8 ГБ.

## Методика

### Набор вопросов

`eval/questions.jsonl` — 50 вопросов в формате дежурного («клиент пишет…»,
«в логах вижу…»):

- 40 по корпусу. У каждого — ожидаемый runbook, эталонный ответ и 1–3 ключевых
  факта (имя таблицы, команда, метрика), которые обязаны прозвучать. Покрыты
  все 16 runbook'ов, по 1–4 вопроса на каждый; 2 вопроса требуют двух
  runbook'ов. 8 вопросов межъязыковые: 6 русских к английским runbook'ам (RB-06,
  RB-13, RB-16) и 2 английских к русским.
- 10 вне корпуса — соседние темы, на которые модели легко выдумать
  правдоподобную инструкцию: восстановление PostgreSQL на момент времени,
  consumer lag в Kafka, продление TLS-сертификата, Kubernetes, условия
  дежурств. Правильный ответ — сказать, что в runbook'ах этого нет.

`eval/questions_holdout.jsonl` — отложенный набор, по которому ничего не
подбиралось. 10 вопросов по корпусу заданы коротко и расплывчато, как в рабочем
чате («оплатил по QR, операция уже полчаса в обработке», «в мини-аппе у клиента
ноль, а в MAX деньги видно»), без слов из заголовков runbook'ов; к трём
подходят два runbook'а. 10 вопросов — соседние темы вне корпуса (лимит
пополнения, перевыпуск пластиковой карты, алерт в Grafana, KV-кеш под контекст
32 тыс. токенов, чарджбэк, 3-D Secure); что ответа в корпусе нет, проверено
поиском по тексту.

### Метрики

| Метрика | Что показывает | Считает |
|---|---|---|
| Нужный runbook на 1-м месте (hit@1) | качество поиска и реранка | скрипт |
| Нужный runbook среди 8 лучших фрагментов (hit@8) | нашёл ли поиск документ вообще; в контекст из них идут только runbook'и выше порога | скрипт |
| Ссылка на нужный runbook | дежурный может проверить источник | скрипт |
| Покрытие ключевых фактов | доля фактов из набора, найденных в ответе | скрипт |
| Верные / частично / неверные | вердикт по сути, со сверкой по полному тексту корпуса | судья |
| Честный отказ вне корпуса | сказал «в runbook'ах нет» и не выдумал процедуру | судья |
| Ответы с выдумкой | команды, цифры, имена таблиц, которых нет в корпусе | судья |
| Ложные отказы | «информации нет», хотя она в корпусе есть | судья |
| Ссылка на посторонний runbook | назван документ, из которого ничего не взято | скрипт и судья |
| Ответы с иероглифами | модель сорвалась в китайский | скрипт |
| Строки кода не из runbook'ов | строка блока кода, которой нет в корпусе | скрипт |
| Время, медиана и 95-й перцентиль | полное время `/ask`, отдельно поиск и генерация | скрипт |

Два правила рубрики понижают вердикт независимо от смысла: ответ не на русском
или со ссылкой на runbook, из которого не взято ни одного шага, — не выше
«частично». Дежурный читает по-русски и идёт по ссылке проверять источник;
ссылка не туда стоит ему времени посреди инцидента.

Метрики поиска отделены от метрик ответа: при провале сразу видно, где чинить —
документ не нашёлся (поиск) или нашёлся, а модель ответила плохо (генерация).

### Судьи

Судья получает полный текст всех 16 runbook'ов, эталон и ответ ассистента и
сверяет каждую команду и цифру с источником. Все 50 ответов уходят одним
вызовом (около 60 тыс. токенов на входе и 7 тыс. на выходе) через Claude Code
CLI (`claude -p`, без инструментов и MCP). Основной судья — Claude Sonnet 5.5;
с 01.10 каждый прогон оценивает и второй, Claude Opus 5.5, вслепую: вердиктов
первого он не видит. Внешний судья допустим только потому, что корпус и вопросы
синтетические; для реальных данных судья должен быть локальным, как и сам
ассистент.

Строки кода сверяет скрипт без модели, `eval/check_commands.py`: каждая строка
из блоков кода ответа ищется в тексте runbook'ов. Пробелы схлопываются,
комментарии пропускаются, подстановка вида `<user_id>` принимается только на
месте конкретного значения.

Две ловушки, найденные по ходу:

- Модель судьи задаётся точным id, и в отчёт пишется id, который CLI реально
  вызвал. Алиас `--model sonnet` в установленном тогда CLI означал
  `claude-sonnet-4-6`, а не последнюю модель: алиас со временем переезжает, и
  цифры разных прогонов перестают быть сравнимыми.
- Судья вызывается с `--safe-mode`. Без него `claude -p` подмешивает в контекст
  личный файл настроек пользователя CLI (`~/.claude/CLAUDE.md`) даже при
  заданном системном промпте. С этим файлом шли судьи прогонов до 01.10 12:06,
  в том числе путь 23 → 26 → 33.

Эвристика отказа в скрипте грубая (ищет фразы вида «в runbook'ах нет»), поэтому
итог по отказам ставит судья. `judge.py` собирает и лист ручной проверки
`manual_check.html` на 10 ответов всех типов вердиктов.

### Как запускать

```bash
# фасад :8080 и vLLM :8000 подняты
py eval/run_eval.py --tag qwen2.5-7b        # ~20 мин на 50 вопросов, метрики без судьи
py eval/run_eval.py --questions eval/questions_holdout.jsonl --tag holdout   # отложенный набор
py eval/judge.py eval/runs/<папка прогона>  # вердикты, report.md, лист ручной проверки
py eval/judge.py <папка> --model claude-opus-5-5 --second  # второй судья, основной отчёт не трогает
py eval/judge.py <папка> --report-only      # пересобрать отчёт без вызова судьи
py eval/check_commands.py <папка>           # строки кода из ответов против текста runbook'ов
py eval/regen.py <папка> --gen claude-sonnet-5-5   # тот же контекст, ответ пишет другая модель
py eval/regen.py <папка> --gen GigaChat-2-Max      # то же через API GigaChat (ключ в .env)
```

Ключ GigaChat — `GIGACHAT_AUTH_KEY` в `.env` (в git не попадает). Корневой
сертификат Минцифры подключается только в соединениях с GigaChat
(`eval/certs/`).

Три находки, которые определили настройку:

- **Первая оценка судьи была завышена.** Sonnet 4.6 с рубрикой без правил про
  язык и ссылки ставил 31 верный вместо 20–23. Показателен q35: SQL верный, но
  подписи перепутаны, и дежурный завершил бы не тот процесс — 4.6 и человек
  засчитали, 5.5 нет. Человек при сверке видел вердикт судьи и соглашался с
  ним, поэтому дальше — второй судья вслепую и скрипт.
- **Реранкер нужен ради уверенности, а не точности.** Без него нужный документ
  всё равно находится, но баллы косинуса по корпусу (от 0,55) и вне его (до
  0,63) перекрываются. Балл реранкера разделяет их чисто: по корпусу не ниже
  0,455, вне корпуса не выше 0,112 — на этом стоит порог.
- **Абсолютный порог не переносится на короткие вопросы.** У вопроса «в
  мини-аппе у клиента ноль» нужный runbook первый, но балл низкий: по корпусу
  от 0,021, вне его до 0,133 — порогом не развести. Подбирать порог по
  отложенному набору значит испортить набор, поэтому ниже порога ассистент
  даёт подсказку, а не отказ.
