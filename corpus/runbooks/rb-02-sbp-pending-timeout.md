# СБП-пополнение зависло в PENDING: таймаут колбэка, ручная сверка и доведение

## Симптом

Пользователь (синт.: user_id=10042) оплатил QR-код или СБП-ссылку на сумму 3 000 ₽, средства списаны с его банковского счёта. Статус транзакции (синт.: txn_id=tx_8f3ac1) остаётся `PENDING` более 15 минут; автоконвертация в USD/EUR и зачисление на виртуальную карту (синт.: карта ****1111) не запущены. Алерт в Grafana: сработал по росту `sbp_callback_timeout_total`.

## Область и влияние

Затронуты пользователи, чьи СБП-платежи находятся в `PENDING` без продвижения. Деньги фактически списаны со стороны банка, но не зачислены на карту — прямой финансовый риск для пользователя. При массовом характере (>5 транзакций одновременно) — потенциальный SEV1.

## Диагностика

**1. Проверить статус воркера очереди:**
```bash
docker ps --filter name=laravel-worker
docker logs --tail=100 laravel-worker 2>&1 | grep -E "sbp|callback|tx_8f3ac1"
```
Ожидаемая строка при ошибке:
```
[2026-06-23 03:41:07] production.ERROR: SBP callback timeout for txn_id=tx_8f3ac1 after 900s {"user_id":10042}
```

**2. LogQL в Grafana / Loki:**
```logql
{job="laravel-worker"} |= "sbp" |= "PENDING" | json | line_format "{{.message}}"
{job="sbp-callback"} |= "callback" |= "error"
```

**3. Метрика в Grafana:**
Панель `SBP / Callback Success Rate` → дашборд `Payments Overview`.
Метрика: `rate(sbp_callback_received_total[5m])` — если близка к нулю при ненулевом `sbp_payment_initiated_total`, колбэки не доходят.

**4. SQL-запрос состояния транзакции:**
```sql
SELECT id, user_id, status, amount_rub, created_at, updated_at, meta->>'sbp_operation_id' AS sbp_op
FROM transactions
WHERE id = 'tx_8f3ac1';
```

**5. Проверить доступность эндпоинта колбэка СБП:**
```bash
curl -v -o /dev/null -s -w "%{http_code}" https://api.internal/sbp/callback/health
ss -tlnp | grep :443
```

## Решение

1. **Получить `sbp_operation_id`** из поля `meta` транзакции (см. SQL выше).
2. **Запросить сверку у банка-партнёра** через внутренний API или вручную через ЛК банка; подтвердить статус операции по `sbp_operation_id`.
3. Если банк подтверждает успешное списание — **вручную запустить доведение** (временный workaround). ⚠️ Перед запуском убедиться, что зачисление ещё НЕ выполнено (`card_credited_at IS NULL` в SQL ниже), иначе возможно повторное зачисление. Команда идемпотентна по `txn_id`; `--force` только снимает блокировку зависшего `PENDING`, но не отключает защиту от двойного зачисления:
```bash
docker exec laravel-app php artisan sbp:finalize-transaction --txn=tx_8f3ac1 --force
```
4. Убедиться, что автоконвертация и зачисление прошли (значения должны заполниться, статус — стать терминальным):
```sql
SELECT status, card_credited_at, converted_amount_usd FROM transactions WHERE id = 'tx_8f3ac1';
```
5. Если банк сообщает, что **списание было, но доведение невозможно** — перевести транзакцию в `FAILED` и инициировать возврат через `php artisan sbp:refund --txn=tx_8f3ac1`. Если банк сообщает, что **списания не было** (операция не прошла) — перевести транзакцию в `FAILED` без возврата (возвращать нечего; возврат несписанной суммы создаст недостачу).
6. После стабилизации — зафиксировать инцидент в Яндекс Трекере и проверить очередь на наличие других зависших `PENDING`.

## Эскалация

- **L1:** Принять обращение, зафиксировать `txn_id` и `user_id` (маскированно), проверить статус транзакции через ЛК поддержки. Если `PENDING` >15 мин — немедленно передать L2 с указанием `txn_id`, времени оплаты и банка-отправителя.
- **L2:** Выполнить диагностику (п. 1–5), проверить логи воркера и метрики колбэков. При подтверждённом списании — выполнить ручное доведение. Если ручной finalize не помогает или затронуто >5 транзакций — эскалировать L3.
- **L3 (дежурный DevOps/разработчик):** Получить от L2 дамп логов (`docker logs laravel-worker > /tmp/worker.log`), результат SQL-запроса, скриншот Grafana-панели и ответ банка. Расследовать причину потери колбэка (сетевой экран, смена IP банка, ошибка TLS). Завести задачу в Яндекс Трекере с тегом `sbp-incident`.
