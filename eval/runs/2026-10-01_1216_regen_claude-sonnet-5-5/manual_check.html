q03 · судья: верно

Подтвердили, что вебхук от эквайера потерялся. Как вручную довести зачисление и кому это разрешено делать?

Эталон из набора

RB-01: запросить у эквайера повторную отправку события; временный workaround — docker exec payment-service php artisan payment:replay --txn <txn_id>, только L2/L3 и только после проверки, что записи в webhook_events нет.

Ответ ассистента
## Ручное зачисление при потере вебхука (RB-01, «Решение», п. 1 и п. 3)

**Кому разрешено:** только L2/L3. Команда зачисления — временный workaround. L1 её выполнять не должен: при подтверждённой потере он передаёт обращение L2 немедленно (менее чем за 10 минут).

**Шаги:**

1. Убедиться, что Nginx принял запрос (шаг 1 диагностики):
```bash
docker logs nginx --since 10m 2>&1 | grep "POST /api/webhooks/payment"
```
2. Если Nginx запрос не принял, проверить сертификат и firewall на стороне эквайера.
3. Запросить повторную отправку события у эквайера через его портал или API.
4. Перед ручным запуском убедиться, что записи в `webhook_events` нет (шаг 3 диагностики):
```sql
SELECT event_id, txn_id, status, created_at, processed_at
FROM webhook_events
WHERE txn_id = 'tx_8f3ac1'
ORDER BY created_at;
```
Отсутствие ряда означает, что вебхук не дошёл.
5. Только после этого вручную запустить зачисление:
```bash
docker exec payment-service php artisan payment:replay --txn tx_8f3ac1
```
6. Создать тикет в Яндекс Трекере с типом «Инцидент» и приложить `event_id`, `txn_id` и дамп из `webhook_events`.

**Важно:** использовать команду `payment:replay` можно только при подтверждённой потере и после проверки, что записи в `webhook_events` нет.

**Дополнительно по эскалации:** если затронуто более 5 пользователей, L2 должен немедленно эскалировать случай в L3. Масштаб оценивается запросом из runbook'а:
```sql
SELECT COUNT(*) FROM webhook_events WHERE status='pending' AND created_at > NOW()-INTERVAL '30 min'
```

Источник: RB-01 — Платёжный вебхук — потеря или дублирование события от эквайера

## Немедленное исправление

**1. Найдите контейнер, который всё ещё использует старый секрет.** Для этого выполните шаг 2 диагностики:

Добавьте в runbook ротации секретов smoke-тест: отправьте тестовый вебхук с новым HMAC и убедитесь, что вернулся HTTP 200, до вывода из обращения старого секрета.

Если повтор недоступен или зависших транзакций больше 200, эскалируйте на L3 (дежурный DevOps и руководитель бэкенда). Для L3 приложите дамп `docker logs webhook-handler`, выгрузку из Loki, результат SQL по зависшим транзакциям и номер обращения в поддержку эквайера.

Дельта сверки 5 000 рублей, сейчас ночь. Будить L2 или можно подождать до утра?

Эталон из набора

RB-07: будить L2 немедленно — при дельте больше 100 ₽ или больше 10 транзакций ждать утра нельзя. Если причина не найдена за 60 минут или дельта больше 10 000 ₽ — подключать L3.

Ответ ассистента
**Будить L2 нужно, ждать утра нельзя.**

Согласно разделу «Эскалация» RB-07 для L1: если дельта > 100 ₽ или расходящихся транзакций > 10, нужно немедленно будить L2 и не ждать утра. Дельта 5 000 ₽ заметно превышает порог в 100 ₽. Кроме того, при дельте > 1 000 ₽ требуется ручная сверка до открытия следующего операционного дня.

Что делать дальше:

**L1 (сейчас):**
- Проверить алерт в Grafana.
- Зафиксировать дельту и количество расходящихся транзакций.
- Немедленно разбудить L2.

**L2 (после подъёма):**
- Запустить SQL-запросы из раздела «Диагностика» и установить причину (курс, округление или дублирование).
- Применить workaround при необходимости. Учтите, что временный workaround (тикет с меткой `recon-rounding` и корректировка через `reconciliation_adjustments`) рассчитан на дельту < 50 ₽ с подтверждённой причиной в виде округления, поэтому при 5 000 ₽ он, скорее всего, не подходит.
- Приложить к тикету: дату реестра, значения `db_total`, `bank_total`, список `txn_id` с дельтами.

**Когда звать L3:** если причина не установлена за 60 минут. Порог по дельте для L3 (> 10 000 ₽) пока не достигнут.

Шаги раздела «Решение» (на случай, если L2 установит причину в курсе или округлении):
1. Выгрузить список `txn_id` с дельтой из SQL диагностики (шаг 4).
2. Для каждой транзакции сверить поле `fx_rate` с архивом курсов (`fx_rates`). Если курс расходится, пересчитать сумму вручную и сформировать корректирующую запись в `reconciliation_adjustments`.
3. Временный workaround: только если дельта < 50 ₽ и причина подтверждена как округление. Создать задачу в Яндекс Трекер с меткой `recon-rounding` и провести корректировку через `reconciliation_adjustments` до следующего прогона.
4. Постоянный фикс: привести стратегию округления в коде к `bcmath` с `scale=2` и согласовать с банком единый момент фиксации курса (`created_at` vs `settlement_at`).
5. После правки запустить повторный прогон сверки:

```bash
docker exec recon-service php artisan recon:run --date=2026-06-23 --force
```

Какие метрики vLLM смотреть, если подозреваю переполнение KV-кэша?

Эталон из набора

RB-10: vllm:gpu_cache_usage_perc (близко к 100 %), vllm:num_preemptions_total (растёт), vllm:num_requests_waiting (очередь не рассасывается), p95 e2e latency по vllm:e2e_request_latency_seconds_bucket.

Ответ ассистента
## Метрики vLLM при подозрении на переполнение KV-кэша (RB-10)

Смотрите панель Grafana `AI Assistant / Inference`:

- `histogram_quantile(0.95, sum by (le) (rate(vllm:e2e_request_latency_seconds_bucket[5m])))`: p95 растёт выше 8 с.
- `vllm:gpu_cache_usage_perc`: приближается к 100 %.
- `vllm:num_preemptions_total`: счётчик ненулевой и растёт.
- `vllm:num_requests_waiting`: очередь ожидающих запросов не рассасывается.

Подтвердить можно и по логам vLLM:

```bash
docker logs vllm --since 15m 2>&1 | grep -E "preempt|cache|queue|OOM"
```

Ожидаемая строка: `Running: 12 reqs, Swapped: 3 reqs, Pending: 8 reqs, GPU KV cache usage: 97.4%`

## Решение из runbook'а

**Шаг 1. Снизить concurrency (временный workaround).** Ограничить параллельные запросы к фасаду через Nginx upstream:

```nginx
# /etc/nginx/conf.d/facade.conf — временно
upstream facade {
    server 127.0.0.1:8001;
    keepalive 4;  # было 16
}
```
```bash
nginx -t && nginx -s reload
```

**Шаг 2. Перезапустить vLLM с уменьшенным `max-num-seqs`.** vLLM читает параметры concurrency и памяти из CLI-флагов entrypoint (`vllm serve`), а не из переменных окружения. Передавайте их как аргументы, иначе фикс не применится:

```bash
docker stop vllm
docker run -d --name vllm --gpus all \
  -p 8000:8000 \
  vllm-image:latest \
  --model /models/Qwen2.5-7B-AWQ --quantization awq \
  --max-num-seqs 4 \            # было 16
  --gpu-memory-utilization 0.88
```

После старта убедиться, что сервис отвечает: `curl -s http://localhost:8000/health | jq .`

**Шаг 3. Проверить восстановление метрик.** В Grafana p95 должна опуститься ниже 4 с в течение 3–5 минут.

**Шаг 4 (постфактум).** Настроить `--max-model-len` под реальный рабочий контекст. Если запросы содержат длинный RAG-контекст, обрезать чанки до 512 токенов в pipeline bge-m3. Зафиксировать значения в Ansible-роли `roles/vllm/defaults/main.yml`.

q32 · судья: верно

В Grafana Explore нет свежих логов фасада, хотя Promtail вроде запущен. Что проверить и как починить?

Эталон из набора

RB-13: логи самого promtail (ошибка чтения positions-файла), готовность Loki (curl :3100/ready) и место на диске; содержимое /tmp/positions.yaml; самый частый фикс — остановить promtail, удалить битый positions-файл и запустить заново; при нехватке диска — retention или расширение тома.

Ответ ассистента
Во фрагментах это RB-13 (Loki не принимает логи / отставание Promtail). Контейнер Promtail может работать, а файл positions при этом зависает.

## Что проверить (диагностика)

1. Статус Promtail и его логи:
```bash
docker ps --filter name=promtail
docker logs promtail --tail=100 2>&1 | grep -E "error|warn|lag|positions"
```
Типичная ошибка:
```
level=error msg="error reading positions file" path=/tmp/positions.yaml err="unexpected EOF"
```

2. Готовность Loki и место на диске:
```bash
curl -s http://localhost:3100/ready
df -h /var/lib/docker/volumes/loki_data
```
Ответ `/ready` должен быть `ready`. Если диск заполнен больше чем на 85%, это повод для тревоги.

3. Файл positions. Ищите одинаковые или устаревшие смещения в нескольких циклах опроса:
```bash
docker exec promtail cat /tmp/positions.yaml
```

4. Лаг в Grafana:
   - Дашборд **Loki / Chunks**, панель `Ingester: Log Entries Received Rate`.
   - Проверочный запрос LogQL:
   ```logql
   {job="facade"} |= "error" | json | line_format "{{.ts}} {{.msg}}"
   ```
   - Метрики: если `promtail_read_bytes_total` стоит ровной линией, а `promtail_file_bytes_total` растёт, то смещение чтения (positions) застряло. Растущий разрыв означает, что Promtail отстаёт.

5. WAL и flusher чанков в Loki:
```bash
docker logs loki --tail=200 2>&1 | grep -E "chunk|flush|pressure|OOO"
```

6. Связанные записи в PostgreSQL:
```sql
SELECT created_at, service, message
FROM incident_log
WHERE created_at > NOW() - INTERVAL '1 hour'
  AND service = 'loki'
ORDER BY created_at DESC
LIMIT 20;
```

## Как чинить

**Fix A. Повреждённый файл positions (самая частая причина):**
```bash
docker stop promtail
docker exec promtail rm /tmp/positions.yaml
docker start promtail
docker logs -f promtail
```
Последняя команда нужна, чтобы убедиться, что повторное чтение логов началось. Файл positions находится внутри контейнера Promtail, либо путь берётся из конфига. Порядок команд приведён как в runbook'е. Если `docker exec` на остановленном контейнере не сработает, альтернативы в runbook'е нет, эскалируйте к L2.

Временная мера: `docker restart promtail` сбрасывает лаг в памяти, но не лечит повреждённый файл. Используйте её только как первичную стабилизацию на время диагностики.

**Fix B. Нехватка места в Loki:**

Основное решение: расширить том или ужесточить retention, затем передеплоить. Для этого задайте `limits_config.retention_period` и `compactor.retention_enabled=true` в конфиге Loki.
```bash
docker compose up -d loki
```
Точечное удаление возможно, только если включён retention в compactor. Используйте POST. Удаление выполняется после `delete_request_cancel_period` (по умолчанию 24 ч), поэтому место освободится не сразу.
```bash
curl -s -X POST \
  'http://localhost:3100/loki/api/v1/delete?query={job="test"}&start=1970-01-01T00:00:00Z&end=2020-01-01T00:00:00Z'
```

**Fix C. OOM или crash loop у Loki:**
```bash
docker stats loki
```
Если контейнер перезапускается, увеличьте `mem_limit` в compose и передеплойте.

**Проверка после любого фикса.** Нужен именно range-эндпоинт, а не instant `/query`:
```bash
curl -s -G 'http://localhost:3100/loki/api/v1/query_range' \
  --data-urlencode 'query={job="facade"}' \
  --data-urlencode "start=$(date -d '5 minutes ago' +%s)000000000" \
  --data-urlencode 'limit=5' | jq '.data.result[].values[0]'
```

## Эскалация
- **L1:** подтвердить симптом (в Explore `{job="facade"}` пуст) и выполнить `docker restart promtail`. Если логи вернулись в течение 5 минут, зафиксировать в Yandex Tracker. Иначе передать L2 скриншот Grafana, последние 200 строк `docker logs promtail` и вывод `df -h`.
- **L2:** выполнить диагностику (шаги 1–6), применить Fix A или B и проверить, что скорость приёма восстановилась. Если Loki в crash loop или очистки диска недостаточно, эскалировать к L3. Приложить содержимое positions, логи Loki, отчёт по диску и вывод SQL из `incident_log`.
- **L3 (дежурный DevOps):** подключается, если нужно расширить диск (resize тома в Yandex Cloud через Ansible) или есть подозрение на повреждение данных Loki (перестроение индекса чанков). Приложить полный `docker inspect` для loki и promtail, compose-файл и снапшот Prometheus:
```bash
curl -XPOST http://localhost:9090/api/v1/admin/tsdb/snapshot
```
Для снапшота Prometheus должен быть запущен с `--web.enable-admin-api`.

Если лаг превышает 30 минут, под угрозой SLA по времени решения инцидентов.

q33 · судья: верно

По каким метрикам понять, что Promtail отстаёт от чтения файлов логов?

Эталон из набора

RB-13: promtail_read_bytes_total стоит на месте, а promtail_file_bytes_total продолжает расти — растущий разрыв значит, что Promtail не успевает читать.

Ответ ассистента
Согласно RB-13 (раздел «Диагностика», шаг 4), отставание Promtail видно по двум метрикам:

- `promtail_file_bytes_total` — размер файла логов (продолжает расти);
- `promtail_read_bytes_total` — сколько байт Promtail уже прочитал (позиция чтения).

**Как интерпретировать:**
- Если `promtail_read_bytes_total` выглядит как плоская линия, а `promtail_file_bytes_total` продолжает расти, значит смещение чтения (positions) застряло.
- Растущий разрыв между этими двумя метриками означает, что Promtail отстаёт.

**Дополнительные признаки из того же runbook'а:**
- на дашборде **Loki / Chunks** панель `Ingester: Log Entries Received Rate` показывает падение или отсутствие поступления записей;
- в файле positions одинаковые (застывшие) смещения на протяжении нескольких циклов скрапинга: `docker exec promtail cat /tmp/positions.yaml`;
- срабатывает алерт **LokiIngestionLag > 5m**.
