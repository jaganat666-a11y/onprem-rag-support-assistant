Ожидаемая строка:
```
10.0.0.5 - - [23/Jun/2026:14:31:02 +0000] "POST /api/webhooks/payment HTTP/1.1" 200 42
```

q06 · судья: неверно

Банк ответил, что списания по этой операции СБП не было. Нужно ли оформлять клиенту возврат?

Эталон из набора

RB-02: нет. Если списания не было, транзакцию переводят в FAILED без возврата — возвращать нечего, возврат несписанной суммы создаст недостачу. Возврат (sbp:refund) нужен, только когда списание было, но довести зачисление невозможно.

Ответ ассистента
Да, нужно оформлять возврат клиенту. В соответствии с описанным в runbook'е процессом, если банк сообщает, что списания не было (операция не прошла), то транзакция должна быть переведена в состояние `FAILED` без возврата. Возврат несписанной суммы может создать недостачу. Поэтому правильный шаг — инициировать возврат через команду:

```bash
docker exec laravel-app php artisan sbp:refund --txn=tx_8f3ac1
```
⚠️ Этих строк нет в runbook'ах — не выполнять без проверки:
- `docker exec laravel-app php artisan sbp:refund --txn=tx_8f3ac1`

Источник: RB-02 — СБП-пополнение зависло в PENDING: таймаут колбэка, ручная сверка и доведение

Комментарий судьи: Ответ «да, оформлять возврат» противоречит корпусу: если списания не было, транзакция переводится в FAILED без возврата.

q25 · судья: верно

p95 ответов ассистента выросла до 15 секунд, в логах vLLM preemption. Что делать?

Эталон из набора

RB-10: временно снизить конкурентность запросов к фасаду (keepalive в upstream Nginx); перезапустить vLLM с меньшим --max-num-seqs (4 вместо 16) — флагом CLI, не переменной окружения; проверить, что p95 опустилась ниже 4 с; постфактум подобрать --max-model-len и длину RAG-чанков.

Ответ ассистента
### Шаг 1. Снизить concurrency (временный workaround).
Ограничить параллельные запросы к фасаду через Nginx upstream:
```nginx
# /etc/nginx/conf.d/facade.conf — временно
upstream facade {
    server 127.0.0.1:8001;
    keepalive 4;  # было 16
}
```
```bash
nginx -t && nginx -s reload
```

### Шаг 2. Перезапустить vLLM с уменьшенным `max-num-seqs`.
Параметры concurrency и памяти vLLM читает из CLI-флагов entrypoint (`vllm serve`), а НЕ из переменных окружения — передаём их как аргументы, иначе фикс не применится:
```bash
docker stop vllm
docker run -d --name vllm --gpus all \
  -p 8000:8000 \
  vllm-image:latest \
  --model /models/Qwen2.5-7B-AWQ --quantization awq \
  --max-num-seqs 4 \            # было 16
  --gpu-memory-utilization 0.88
```
После старта убедиться: `curl -s http://localhost:8000/health | jq .`

### Шаг 3. Проверить восстановление метрик — в Grafana p95 должна опуститься ниже 4 с в течение 3–5 мин.

### Шаг 4 (постфактум). Настроить `--max-model-len` под реальный рабочий контекст (если запросы содержат длинный RAG-контекст — обрезать чанки до 512 токенов в pipeline bge-m3). Зафиксировать значения в Ansible-роли `roles/vllm/defaults/main.yml`.

Источник: RB-10 — Высокая latency p95 ассистента: переполнение KV-cache и preemption

q37 · судья: верно

Как настроить ротацию docker-логов, чтобы диск больше не забивался?

Эталон из набора

RB-15: в docker-compose.yml задать logging: driver json-file с options max-size: "50m" и max-file: "5"; раскатать через Ansible (playbooks/docker_log_rotation.yml).

Ответ ассистента
Для настройки ротации docker-логов и предотвращения переполнения диска необходимо выполнить следующие шаги:

1. Открыть файл `docker-compose.yml` для редактирования.
2. В секции `logging` добавить параметры для ограничения размера и количества файлов логов:
```yaml
logging:
  driver: "json-file"
  options:
    max-size: "50m"
    max-file: "5"
```
3. Сохранить изменения в файле `docker-compose.yml`.
4. Применить изменения через Ansible:
```bash
ansible-playbook -i inventory/prod playbooks/docker_log_rotation.yml
```

Эти шаги помогут автоматически управлять размером и количеством файлов логов, предотвращая переполнение диска.

Источник: RB-15 — Диск заполнен на ноде — контейнеры в CrashLoop

q39 · судья: частично

A user paid via SBP, the money left their bank account, but the transaction has been stuck in PENDING for 20 minutes. What should the on-call engineer do?

Эталон из набора

RB-02: проверить laravel-worker и логи колбэка; взять sbp_operation_id из meta транзакции; запросить сверку у банка-партнёра; если списание подтверждено и card_credited_at IS NULL — довести вручную: php artisan sbp:finalize-transaction --txn=<txn_id> --force.

Ответ ассистента
На основе предоставленных runbook'ов, на-call инженер должен выполнить следующие шаги:

1. **Проверить статус воркера очереди:**
```bash
docker ps --filter name=laravel-worker
docker logs --tail=100 laravel-worker 2>&1 | grep -E "sbp|callback|tx_8f3ac1"
```

2. **LogQL в Grafana / Loki:**
```logql
{job="laravel-worker"} |= "sbp" |= "PENDING" | json | line_format "{{.message}}"
{job="sbp-callback"} |= "callback" |= "error"
```

3. **Метрика в Grafana:**
Панель `SBP / Callback Success Rate` → дашборд `Payments Overview`.
Метрика: `rate(sbp_callback_received_total[5m])` — если близка к нулю при ненулевом `sbp_payment_initiated_total`, колбэки не доходят.

4. **SQL-запрос состояния транзакции:**
```sql
SELECT id, user_id, status, amount_rub, created_at, updated_at, meta->>'sbp_operation_id' AS sbp_op
FROM transactions
WHERE id = 'tx_8f3ac1';
```

5. **Проверить доступность эндпоинта колбэка СБП:**
```bash
curl -v -o /dev/null -s -w "%{http_code}" https://api.internal/sbp/callback/health
ss -tlnp | grep :443
```

6. **Получить `sbp_operation_id`** из поля `meta` транзакции (см. SQL выше).

7. **Запросить сверку у банка-партнёра** через внутренний API или вручную через ЛК банка; подтвердить статус операции по `sbp_operation_id`.

8. **Вручную запустить доведение** (временный workaround):
```bash
docker exec laravel-app php artisan sbp:finalize-transaction --txn=tx_8f3ac1 --force
```

9. **Убедиться, что автоконвертация и зачисление прошли:**
```sql
SELECT status, card_credited_at, converted_amount_usd FROM transactions WHERE id = 'tx_8f3ac1';
```

10. **После стабилизации — зафиксировать инцидент в Яндекс Трекере и проверить очередь на наличие других зависших `PENDING`.**

Если транзакция не может быть доведена, необходимо перевести её в `FAILED` и инициировать возврат через `php artisan sbp:refund --txn=tx_8f3ac1` или перевести в `FAILED` без возврата, в зависимости от ответа банка.

Источник: RB-02 — СБП-пополнение зависло в PENDING: таймаут колбэка, ручная сверка и доведение

Комментарий судьи: Нет обязательной проверки card_credited_at IS NULL перед finalize, команда подана после запроса к банку без условия.

q40 · судья: верно

How do I find which PostgreSQL query is blocking the others and release the lock?

Эталон из набора

RB-14: запрос к pg_locks с джойном к pg_stat_activity (заблокированный NOT granted, блокирующий granted) даёт blocking_pid; временный workaround — SELECT pg_terminate_backend(<blocking_pid>).

Ответ ассистента
Чтобы найти блокирующий запрос и освободить его, нужно выполнить следующие шаги:

1. Найти цепочку блокировок:
```sql
SELECT blocked.pid AS blocked_pid, blocked_act.query AS blocked_query,
       blocking.pid AS blocking_pid, blocking_act.query AS blocking_query
FROM pg_locks blocked
JOIN pg_stat_activity blocked_act   ON blocked_act.pid = blocked.pid
JOIN pg_locks blocking ON blocking.locktype = blocked.locktype
  AND blocking.database     IS NOT DISTINCT FROM blocked.database
  AND blocking.relation     IS NOT DISTINCT FROM blocked.relation
  AND blocking.page         IS NOT DISTINCT FROM blocked.page
  AND blocking.tuple        IS NOT DISTINCT FROM blocked.tuple
  AND blocking.virtualxid   IS NOT DISTINCT FROM blocked.virtualxid
  AND blocking.transactionid IS NOT DISTINCT FROM blocked.transactionid
  AND blocking.classid      IS NOT DISTINCT FROM blocked.classid
  AND blocking.objid        IS NOT DISTINCT FROM blocked.objid
  AND blocking.objsubid     IS NOT DISTINCT FROM blocked.objsubid
  AND blocking.pid != blocked.pid
JOIN pg_stat_activity blocking_act  ON blocking_act.pid = blocking.pid
WHERE NOT blocked.granted AND blocking.granted;
```

2. Завершить блокирующий процесс:
```sql
SELECT pg_terminate_backend(<blocking_pid>);
```

Замените `<blocking_pid>` на PID блокирующего процесса, который был найден на первом шаге.

Источник: RB-14 — PostgreSQL — исчерпан пул соединений, блокировки от long-running запроса
