q04 · судья: частично

Платёж по СБП висит в PENDING уже 20 минут, у клиента деньги списаны. Что делать дежурному?

Эталон из набора

RB-02: проверить воркер laravel-worker и логи колбэка; взять sbp_operation_id из meta транзакции; запросить сверку у банка-партнёра; если банк подтвердил списание и card_credited_at IS NULL — довести вручную: php artisan sbp:finalize-transaction --txn=<txn_id> --force; затем проверить статус и зачисление.

Ответ ассистента
Дежурному инженеру следует выполнить следующие шаги:

1. **Проверить статус воркера очереди:**
```bash
docker ps --filter name=laravel-worker
docker logs --tail=100 laravel-worker 2>&1 | grep -E "sbp|callback|tx_8f3ac1"
```

2. **LogQL в Grafana / Loki:**
```logql
{job="laravel-worker"} |= "sbp" |= "PENDING" | json | line_format "{{.message}}"
{job="sbp-callback"} |= "callback" |= "error"
```

3. **Метрика в Grafana:**
Панель `SBP / Callback Success Rate` → дашборд `Payments Overview`.
Метрика: `rate(sbp_callback_received_total[5m])` — если близка к нулю при ненулевом `sbp_payment_initiated_total`, колбэки не доходят.

4. **SQL-запрос состояния транзакции:**
```sql
SELECT id, user_id, status, amount_rub, created_at, updated_at, meta->>'sbp_operation_id' AS sbp_op
FROM transactions
WHERE id = 'tx_8f3ac1';
```

5. **Проверить доступность эндпоинта колбэка СБП:**
```bash
curl -v -o /dev/null -s -w "%{http_code}" https://api.internal/sbp/callback/health
ss -tlnp | grep :443
```

6. **Получить `sbp_operation_id`** из поля `meta` транзакции (см. SQL выше).

7. **Запросить сверку у банка-партнёра** через внутренний API или вручную через ЛК банка; подтвердить статус операции по `sbp_operation_id`.

8. **Вручную запустить доведение** (временный workaround):
```bash
docker exec laravel-app php artisan sbp:finalize-transaction --txn=tx_8f3ac1 --force
```

9. **Убедиться, что автоконвертация и зачисление прошли** (значения должны заполниться, статус — стать терминальным):
```sql
SELECT status, card_credited_at, converted_amount_usd FROM transactions WHERE id = 'tx_8f3ac1';
```

10. **После стабилизации — зафиксировать инцидент в Яндекс Трекере и проверить очередь на наличие других зависших `PENDING`.**

Если платёж висит в PENDING более 20 минут, дежурный инженер должен следовать этим шагам для решения проблемы.

Источник: RB-02 — СБП-пополнение зависло в PENDING: таймаут колбэка, ручная сверка и доведение

Комментарий судьи: finalize с --force дан без предварительной проверки card_credited_at IS NULL, есть риск двойного зачисления.

q19 · судья: верно

Как вытащить из базы транзакции, у которых сумма не совпадает с банковским реестром?

Эталон из набора

RB-07: JOIN transactions с bank_recon_import по b.bank_txn_ref = t.external_ref за вчерашнюю дату с условием ABS(t.amount_rub - b.bank_amount_rub) > 0.01, сортировка по величине дельты.

Ответ ассистента
Чтобы вытащить из базы транзакции, у которых сумма не совпадает с банковским реестром, можно использовать следующую SQL-запрос:

```sql
SELECT
    t.id                         AS txn_id,
    t.user_id,
    t.amount_rub,
    t.amount_usd,
    t.fx_rate,
    t.created_at,
    b.bank_amount_rub,
    (t.amount_rub - b.bank_amount_rub) AS delta_rub
FROM transactions t
JOIN bank_recon_import b ON b.bank_txn_ref = t.external_ref
WHERE DATE(t.created_at) = CURRENT_DATE - 1
  AND ABS(t.amount_rub - b.bank_amount_rub) > 0.01
ORDER BY ABS(delta_rub) DESC
LIMIT 50;
```

Этот запрос выбирает транзакции, где сумма в базе данных (`t.amount_rub`) не совпадает с суммой в банковском реестре (`b.bank_amount_rub`), и сортирует их по абсолютной величине разницы (`delta_rub`).

Источник: RB-07 — Расхождение сверки — сумма в БД не совпадает с банковским реестром

q24 · судья: частично

Как по Grafana подтвердить, что vLLM упал именно из-за нехватки видеопамяти?

Эталон из набора

RB-09: дашборд vLLM Observability, панель VRAM Used (MiB) — метрика nvidia_smi_memory_used_bytes из gpu-exporter :9835; перед падением значение упирается в ~8000 MiB.

Ответ ассистента
Для подтверждения, что vLLM упал именно из-за нехватки видеопамяти, можно использовать следующие шаги:

1. Открыть дашборд **"vLLM Observability"**, панель `VRAM Used (MiB)` (источник: `nvidia_smi_memory_used_bytes` из gpu-exporter `:9835`). Убедиться, что перед падением значение упиралось в ~8000 MiB.

   ```promql
   nvidia_smi_memory_used_bytes{gpu="0"} / 1024 / 1024
   ```

2. Проверить логи GPU в Grafana с помощью LogQL:

   ```logql
   {job="gpu_exporter"} |= "error" | json | line_format "{{.ts}} {{.level}} {{.msg}}"
   ```

3. Искать строки логов, которые указывают на нехватку видеопамяти:

   ```
   torch.cuda.OutOfMemoryError: CUDA out of memory. Tried to allocate 1.80 GiB (GPU 0; 8.00 GiB total capacity; 7.43 GiB already allocated)
   ```

Эти шаги помогут подтвердить, что vLLM упал именно из-за нехватки видеопамяти.

Источник: RB-09 — vLLM OOM — контейнер упал из-за нехватки VRAM

Комментарий судьи: Основной ответ верный, но LogQL с job="gpu_exporter" выдуман и в корпусе его нет.

q33 · судья: верно

По каким метрикам понять, что Promtail отстаёт от чтения файлов логов?

Эталон из набора

RB-13: promtail_read_bytes_total стоит на месте, а promtail_file_bytes_total продолжает расти — растущий разрыв значит, что Promtail не успевает читать.

Ответ ассистента
По метрикам `promtail_read_bytes_total` и `promtail_file_bytes_total` можно понять, что Promtail отстает от чтения файлов логов. Если `promtail_read_bytes_total` показывает статичное значение, а `promtail_file_bytes_total` продолжает расти, это указывает на то, что Promtail застрял на определённом месте в файле логов. Это означает, что Promtail не читает новые данные из файлов логов.

Источник: RB-13 — Loki Not Ingesting Logs / Promtail Lag

q34 · судья: верно

В логах Laravel: remaining connection slots are reserved, клиенты не могут пополнить карту. Что делать?

Эталон из набора

RB-14: посмотреть соединения в pg_stat_activity, найти блокирующий запрос через pg_locks; временно завершить блокирующий бэкенд SELECT pg_terminate_backend(<pid>); перезапустить PgBouncer и проверить, что его пул не превышает max_connections; постоянно — EXPLAIN ANALYZE и оптимизация запроса.

Ответ ассистента
В данном случае следует следовать следующим шагам:

1. Проверить число активных соединений:
```bash
docker exec -it postgres psql -U app_user -d payworld -c \
  "SELECT count(*), state FROM pg_stat_activity GROUP BY state;"
```

2. Найти long-running и блокирующие запросы:
```sql
SELECT pid, now() - pg_stat_activity.query_start AS duration,
       usename, application_name, state, wait_event_type, wait_event,
       left(query, 120) AS query_snippet
FROM pg_stat_activity
WHERE state != 'idle'
  AND query_start < now() - interval '30 seconds'
ORDER BY duration DESC;
```

3. Найти цепочку блокировок:
```sql
SELECT blocked.pid AS blocked_pid, blocked_act.query AS blocked_query,
       blocking.pid AS blocking_pid, blocking_act.query AS blocking_query
FROM pg_locks blocked
JOIN pg_stat_activity blocked_act   ON blocked_act.pid = blocked.pid
JOIN pg_locks blocking ON blocking.locktype = blocked.locktype
  AND blocking.database     IS NOT DISTINCT FROM blocked.database
  AND blocking.relation     IS NOT DISTINCT FROM blocked.relation
  AND blocking.page         IS NOT DISTINCT FROM blocked.page
  AND blocking.tuple        IS NOT DISTINCT FROM blocked.tuple
  AND blocking.virtualxid   IS NOT DISTINCT FROM blocked.virtualxid
  AND blocking.transactionid IS NOT DISTINCT FROM blocked.transactionid
  AND blocking.classid      IS NOT DISTINCT FROM blocked.classid
  AND blocking.objid        IS NOT DISTINCT FROM blocked.objid
  AND blocking.objsubid     IS NOT DISTINCT FROM blocked.objsubid
  AND blocking.pid != blocked.pid
JOIN pg_stat_activity blocking_act  ON blocking_act.pid = blocking.pid
WHERE NOT blocked.granted AND blocking.granted;
```

4. Логи контейнера:
```bash
docker logs --tail=100 postgres 2>&1 | grep -E "ERROR|FATAL|connection"
```

5. Метрика в Grafana: панель `PostgreSQL / Connections` → график `pg_stat_activity_count` по `state`; алерт `pg_connections_near_limit` (порог 90% от `max_connections`).

6. LogQL в Loki:
```
{job="laravel"} |= "remaining connection slots"
```

7. Временный workaround (немедленно):
```sql
SELECT pg_terminate_backend(<blocking_pid>);
```

8. Фикс пула:
```bash
# Проверить, запущен ли PgBouncer
docker ps | grep pgbouncer

# Перезапустить PgBouncer для сброса зависших клиентов
docker restart pgbouncer
```

9. Убедиться, что суммарный backend-пул PgBouncer не превышает `max_connections` PostgreSQL за вычетом зарезервированных суперъюзерских слотов. После нормализации числа соединений проверить алерт в Grafana — он должен закрыться в течение 2 минут.

10. Постоянный фикс: разобраться с причиной long-running запроса (`EXPLAIN ANALYZE`), добавить индекс или оптимизировать ORM-запрос; при необходимости поднять `max_connections` в `postgresql.conf` и пересмотреть `pool_size` в PgBouncer.

Источник: RB-14 — PostgreSQL — исчерпан пул соединений, блокировки от long-running запроса

q40 · судья: верно

How do I find which PostgreSQL query is blocking the others and release the lock?

Эталон из набора

RB-14: запрос к pg_locks с джойном к pg_stat_activity (заблокированный NOT granted, блокирующий granted) даёт blocking_pid; временный workaround — SELECT pg_terminate_backend(<blocking_pid>).

Ответ ассистента
Чтобы найти блокирующий запрос и освободить его, нужно выполнить следующие шаги:

1. Найти цепочку блокировок:
```sql
SELECT blocked.pid AS blocked_pid, blocked_act.query AS blocked_query,
       blocking.pid AS blocking_pid, blocking_act.query AS blocking_query
FROM pg_locks blocked
JOIN pg_stat_activity blocked_act   ON blocked_act.pid = blocked.pid
JOIN pg_locks blocking ON blocking.locktype = blocked.locktype
  AND blocking.database     IS NOT DISTINCT FROM blocked.database
  AND blocking.relation     IS NOT DISTINCT FROM blocked.relation
  AND blocking.page         IS NOT DISTINCT FROM blocked.page
  AND blocking.tuple        IS NOT DISTINCT FROM blocked.tuple
  AND blocking.virtualxid   IS NOT DISTINCT FROM blocked.virtualxid
  AND blocking.transactionid IS NOT DISTINCT FROM blocked.transactionid
  AND blocking.classid      IS NOT DISTINCT FROM blocked.classid
  AND blocking.objid        IS NOT DISTINCT FROM blocked.objid
  AND blocking.objsubid     IS NOT DISTINCT FROM blocked.objsubid
  AND blocking.pid != blocked.pid
JOIN pg_stat_activity blocking_act  ON blocking_act.pid = blocking.pid
WHERE NOT blocked.granted AND blocking.granted;
```

2. Завершить блокирующий процесс:
```sql
SELECT pg_terminate_backend(<blocking_pid>);
```

Замените `<blocking_pid>` на PID блокирующего процесса, который был найден на первом шаге.

Источник: RB-14 — PostgreSQL — исчерпан пул соединений, блокировки от long-running запроса
