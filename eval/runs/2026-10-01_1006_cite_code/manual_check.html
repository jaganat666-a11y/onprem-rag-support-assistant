q03 · судья: частично

Подтвердили, что вебхук от эквайера потерялся. Как вручную довести зачисление и кому это разрешено делать?

Эталон из набора

RB-01: запросить у эквайера повторную отправку события; временный workaround — docker exec payment-service php artisan payment:replay --txn <txn_id>, только L2/L3 и только после проверки, что записи в webhook_events нет.

Ответ ассистента
Если вебхук от эквайера потерялся, нужно выполнить следующие шаги для вручной доведки зачисления:

1. **Проверить, дошёл ли вебхук до Nginx:**
```bash
docker logs nginx --since 10m 2>&1 | grep "POST /api/webhooks/payment"
```

2. **Проверить логи контейнера webhook-handler (Loki / LogQL):**
```logql
{job="webhook-handler"} |= "tx_8f3ac1"
```

3. **Проверить идемпотентность в PostgreSQL:**
```sql
SELECT event_id, txn_id, status, created_at, processed_at
FROM webhook_events
WHERE txn_id = 'tx_8f3ac1'
ORDER BY created_at;
```

4. **Проверить доступность эндпоинта:**
```bash
curl -v -X POST https://pay.example.internal/api/webhooks/payment \
  -H "X-Signature: test" -d '{"event_id":"probe-1","txn_id":"probe"}' 2>&1 | head -20
```

5. **Вручную запустить команду зачисления:**
```bash
docker exec payment-service php artisan payment:replay --txn tx_8f3ac1
```

Эти шаги должны быть выполнены дежурным инженером поддержки, который имеет соответствующие права доступа и разрешение на выполнение таких действий.

Источник: RB-01 — Платёжный вебхук — потеря или дублирование события от эквайера

Комментарий судьи: Не сказано, что replay разрешён только L2/L3, и не упомянут запрос повторной отправки у эквайера; условие «записи в webhook_events нет» размыто.

q33 · судья: частично

По каким метрикам понять, что Promtail отстаёт от чтения файлов логов?

Эталон из набора

RB-13: promtail_read_bytes_total стоит на месте, а promtail_file_bytes_total продолжает расти — растущий разрыв значит, что Promtail не успевает читать.

Ответ ассистента
По метрикам можно понять, что Promtail отстает от чтения файлов логов следующим образом:

1. Проверить метрику `promtail_read_bytes_total`, которая отражает количество байт, прочитанных Promtail.
2. Проверить метрику `promtail_file_bytes_total`, которая отражает размер файла, который Promtail пытается прочитать.
3. Если `promtail_file_bytes_total` продолжает расти, а `promtail_read_bytes_total` остается на месте или растет медленнее, это указывает на то, что Promtail застрял на определенной позиции в файле логов.

Для проверки этих метрик можно использовать следующую команду:

```logql
{job="promtail"} |= "promtail_read_bytes_total" | json | line_format "{{.ts}} {{.msg}}"
{job="promtail"} |= "promtail_file_bytes_total" | json | line_format "{{.ts}} {{.msg}}"
```

Если `promtail_read_bytes_total` остается на месте или растет медленнее, чем `promtail_file_bytes_total`, это указывает на то, что Promtail застрял и может потребоваться восстановление позиций файла логов.

Источник: RB-13 — Loki Not Ingesting Logs / Promtail Lag

Комментарий судьи: Метрики названы верно, но предложены выдуманные LogQL-запросы по именам метрик, которых нет в корпусе.

q36 · судья: частично

Диск на ноде забит, контейнеры в CrashLoop, no space left on device. Как быстро освободить место и не потерять данные?

Эталон из набора

RB-15: усечь самые тяжёлые docker-логи (truncate -s 0 по LogPath, не удалять), docker system prune -f без --volumes; тома postgres/loki не трогать — docker volume prune только после подтверждения L3 и резервной копии; затем перезапустить контейнеры и настроить ротацию логов.

Ответ ассистента
Для быстрого освобождения места на диске и предотвращения потери данных, следует выполнить следующие шаги:

1. **Усечь docker-логи тяжёлых контейнеров:**
```bash
truncate -s 0 $(docker inspect --format='{{.LogPath}}' vllm_container)
truncate -s 0 $(docker inspect --format='{{.LogPath}}' loki)
```

2. **Удалить неиспользуемые docker-объекты:**
```bash
docker system prune -f
```

3. **Настроить ротацию логов (постоянное решение):**
```yaml
logging:
  driver: "json-file"
  options:
    max-size: "50m"
    max-file: "5"
```

4. **Применить через Ansible:**
```bash
ansible-playbook -i inventory/prod playbooks/docker_log_rotation.yml
```

5. **Перезапустить контейнеры в CrashLoop:**
```bash
docker compose up -d --force-recreate
docker ps -a  # убедиться, что все Up
```

6. **Проверить восстановление:**
```bash
curl -s http://localhost:8001/health | jq .
df -h /
```

Эти шаги помогут быстро освободить место на диске и предотвратить дальнейшие проблемы с заполнением диска.

Источник: RB-15 — Диск заполнен на ноде — контейнеры в CrashLoop

Комментарий судьи: Не предупреждено, что тома postgres/loki трогать нельзя (volume prune только с подтверждения L3), хотя вопрос про сохранность данных.

q39 · судья: верно

A user paid via SBP, the money left their bank account, but the transaction has been stuck in PENDING for 20 minutes. What should the on-call engineer do?

Эталон из набора

RB-02: проверить laravel-worker и логи колбэка; взять sbp_operation_id из meta транзакции; запросить сверку у банка-партнёра; если списание подтверждено и card_credited_at IS NULL — довести вручную: php artisan sbp:finalize-transaction --txn=<txn_id> --force.

Ответ ассистента
На дежурстве инженер должен выполнить следующие действия:

1. **Получить `sbp_operation_id`** из поля `meta` транзакции (см. SQL выше).
2. **Запросить сверку у банка-партнёра** через внутренний API или вручную через ЛК банка; подтвердить статус операции по `sbp_operation_id`.
3. Если банк подтверждает успешное списание — **вручную запустить доведение** (временный workaround). Перед запуском убедиться, что зачисление ещё НЕ выполнено (`card_credited_at IS NULL` в SQL ниже), иначе возможно повторное зачисление. Команда идемпотентна по `txn_id`; `--force` только снимает блокировку зависшего `PENDING`, но не отключает защиту от двойного зачисления:
```bash
docker exec laravel-app php artisan sbp:finalize-transaction --txn=tx_8f3ac1 --force
```
4. Убедиться, что автоконвертация и зачисление прошли (значения должны заполниться, статус — стать терминальным):
```sql
SELECT status, card_credited_at, converted_amount_usd FROM transactions WHERE id = 'tx_8f3ac1';
```
5. Если банк сообщает, что **списание было, но доведение невозможно** — перевести транзакцию в `FAILED` и инициировать возврат через `php artisan sbp:refund --txn=tx_8f3ac1`. Если банк сообщает, что **списания не было** (операция не прошла) — перевести транзакцию в `FAILED` без возврата (возвращать нечего; возврат несписанной суммы создаст недостачу).
6. После стабилизации — зафиксировать инцидент в Яндекс Трекере и проверить очередь на наличие других зависших `PENDING`.

Источник: RB-02 — СБП-пополнение зависло в PENDING: таймаут колбэка, ручная сверка и доведение
