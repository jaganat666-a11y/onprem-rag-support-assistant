q04 · судья: частично

Платёж по СБП висит в PENDING уже 20 минут, у клиента деньги списаны. Что делать дежурному?

Эталон из набора

RB-02: проверить воркер laravel-worker и логи колбэка; взять sbp_operation_id из meta транзакции; запросить сверку у банка-партнёра; если банк подтвердил списание и card_credited_at IS NULL — довести вручную: php artisan sbp:finalize-transaction --txn=<txn_id> --force; затем проверить статус и зачисление.

Ответ ассистента
### Шаги решения согласно RB-02:

1. **Получить `sbp_operation_id`:**
   ```sql
   SELECT id, user_id, status, amount_rub, created_at, updated_at, meta->>'sbp_operation_id' AS sbp_op
   FROM transactions
   WHERE id = 'tx_8f3ac1';
   ```
   
2. **Запросить сверку у банка-партнёра**: Подтвердите статус операции по полученному ранее `sbp_operation_id`.

3. **Вручную запустить доведение**, если банк подтвердил успешное списание средств:
   ```bash
   docker exec laravel-app php artisan sbp:finalize-transaction --txn=tx_8f3ac1 --force
   ```

4. **Проверить состояние транзакции** после запуска доведения:
   ```sql
   SELECT status, card_credited_at, converted_amount_usd FROM transactions WHERE id = 'tx_8f3ac1';
   ```

5. Если банку удалось успешно провести операцию, но доведение завершить невозможно — переведите транзакцию в `FAILED` и выполните возврат:
   ```bash
   php artisan sbp:refund --txn=tx_8f3ac1
   ```

6. Если банк сообщил об отмене операции (средства не были списаны) — просто переведите транзакцию в `FAILED` без выполнения возврата.

7. Зафиксируйте инцидент в Яндекс Трекере и проверьте очередь на наличие других зависших платежей в состоянии `PENDING`.

Источник: RB-02 — СБП-пополнение зависло в PENDING: таймаут колбэка, ручная сверка и доведение

Комментарий судьи: Нет обязательной проверки card_credited_at IS NULL перед finalize и проверки воркера.

- `docker exec laravel-app php artisan sbp:finalize-transaction --txn=tx_8f3ac1 --status=failed`

В данном случае оформление возврата пользователю не требуется, так как банк подтвердил отсутствие списания средств. Оформлять возврат можно лишь тогда, когда есть подтверждение успешного списания денег со счета клиента банком.

q26 · судья: верно

Какие метрики vLLM смотреть, если подозреваю переполнение KV-кэша?

Эталон из набора

RB-10: vllm:gpu_cache_usage_perc (близко к 100 %), vllm:num_preemptions_total (растёт), vllm:num_requests_waiting (очередь не рассасывается), p95 e2e latency по vllm:e2e_request_latency_seconds_bucket.

Ответ ассистента
Если подозреваете переполнение KV-кэша, нужно посмотреть следующие метрики vLLM:

- `vllm:gpu_cache_usage_perc`: показывает процент использования GPU KV cache. Приближение к 100 % указывает на возможное переполнение.
- `vllm:num_preemptions_total`: счетчик количества прерываний обработки запросов из-за нехватки ресурсов или заполнения очереди. Ненулевое значение говорит о наличии проблем с ресурсами.
- `vllm:num_requests_waiting`: количество запросов, стоящих в очереди ожидания выполнения. Рост этой метрики свидетельствует о том, что новые запросы не могут быть обработаны сразу.

Эти метрики можно увидеть на панели Grafana `AI Assistant / Inference`.

Источник: RB-10 — Высокая latency p95 ассистента: переполнение KV-cache и preemption

q35 · судья: верно

Как найти в PostgreSQL запрос, который блокирует остальные?

Эталон из набора

RB-14: запрос к pg_locks с джойном к pg_stat_activity, где заблокированный NOT granted, а блокирующий granted, — выдаёт blocked_pid / blocking_pid и тексты запросов; долгие запросы — по pg_stat_activity с query_start старше 30 секунд.

Ответ ассистента
Из runbook RB-14 приведены следующие шаги и команды для поиска блокирующего запроса в PostgreSQL:

### 1. Найти long-running и блокирующие запросы:
```sql
SELECT pid, now() - pg_stat_activity.query_start AS duration,
       usename, application_name, state, wait_event_type, wait_event,
       left(query, 120) AS query_snippet
FROM pg_stat_activity
WHERE state != 'idle'
  AND query_start < now() - interval '30 seconds'
ORDER BY duration DESC;
```

### 2. Найти цепочку блокировок:
```sql
SELECT blocked.pid AS blocked_pid, blocked_act.query AS blocked_query,
       blocking.pid AS blocking_pid, blocking_act.query AS blocking_query
FROM pg_locks blocked
JOIN pg_stat_activity blocked_act   ON blocked_act.pid = blocked.pid
JOIN pg_locks blocking ON blocking.locktype = blocked.locktype
  AND blocking.database     IS NOT DISTINCT FROM blocked.database
  AND blocking.relation     IS NOT DISTINCT FROM blocked.relation
  AND blocking.page         IS NOT DISTINCT FROM blocked.page
  AND blocking.tuple        IS NOT DISTINCT FROM blocked.tuple
  AND blocking.virtualxid   IS NOT DISTINCT FROM blocked.virtualxid
  AND blocking.transactionid IS NOT DISTINCT FROM blocked.transactionid
  AND blocking.classid      IS NOT DISTINCT FROM blocked.classid
  AND blocking.objid        IS NOT DISTINCT FROM blocked.objid
  AND blocking.objsubid     IS NOT DISTINCT FROM blocked.objsubid
  AND blocking.pid != blocked.pid
JOIN pg_stat_activity blocking_act  ON blocking_act.pid = blocking.pid
WHERE NOT blocked.granted AND blocking.granted;
```

Источник: RB-14 — PostgreSQL — исчерпан пул соединений, блокировки от long-running запроса
