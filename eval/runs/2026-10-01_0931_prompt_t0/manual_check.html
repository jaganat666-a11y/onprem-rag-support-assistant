Ночная сверка показала расхождение с банковским реестром на 23,52 ₽ по 4 транзакциям. Какие типичные причины?

Эталон из набора

Ответ ассистента
Типичные причины расхождения с банковским реестром могут быть следующими:

1. Курс фиксируется на `created_at`, а банк считает по курсу `settlement_at` (+5–30 мин).
2. PHP `round($amount, 2)` против банковского `TRUNCATE(amount, 2)`.

Эти причины описаны в разделе "Симптом" и "Диагностика" runbook'а RB-07 — Расхождение сверки — сумма в БД не совпадает с банковским реестром.

q33 · судья: частично

По каким метрикам понять, что Promtail отстаёт от чтения файлов логов?

Эталон из набора

RB-13: promtail_read_bytes_total стоит на месте, а promtail_file_bytes_total продолжает расти — растущий разрыв значит, что Promtail не успевает читать.

Ответ ассистента
По метрикам `promtail_read_bytes_total` и `promtail_file_bytes_total` можно понять, что Promtail отстает от чтения файлов логов. Если `promtail_read_bytes_total` показывает статичное значение, а `promtail_file_bytes_total` продолжает расти, это указывает на то, что Promtail застрял на определённом месте в файле логов.

Используемый LogQL запрос для проверки:
```logql
{job="facade"} |= "error" | json | line_format "{{.ts}} {{.msg}}"
```

Этот запрос поможет проверить, есть ли ошибки в Promtail, которые могут указывать на проблемы с чтением файлов логов.

Используемый bash запрос для проверки метрик:
```bash
curl -s -G 'http://localhost:3100/loki/api/v1/query_range' \
  --data-urlencode 'query=promtail_read_bytes_total' \
  --data-urlencode "start=$(date -d '5 minutes ago' +%s)000000000" \
  --data-urlencode 'limit=5' | jq '.data.result[].values[0]'

curl -s -G 'http://localhost:3100/loki/api/v1/query_range' \
  --data-urlencode 'query=promtail_file_bytes_total' \
  --data-urlencode "start=$(date -d '5 minutes ago' +%s)000000000" \
  --data-urlencode 'limit=5' | jq '.data.result[].values[0]'
```

Эти запросы позволят сравнить значения `promtail_read_bytes_total` и `promtail_file_bytes_total` в течение последних 5 минут, чтобы выявить отставание Promtail.

q40 · судья: верно

How do I find which PostgreSQL query is blocking the others and release the lock?

Эталон из набора

RB-14: запрос к pg_locks с джойном к pg_stat_activity (заблокированный NOT granted, блокирующий granted) даёт blocking_pid; временный workaround — SELECT pg_terminate_backend(<blocking_pid>).

Ответ ассистента
Для того чтобы найти блокирующий запрос и освободить его, нужно выполнить следующие шаги:

1. Найти long-running и блокирующие запросы:
```sql
SELECT pid, now() - pg_stat_activity.query_start AS duration,
       usename, application_name, state, wait_event_type, wait_event,
       left(query, 120) AS query_snippet
FROM pg_stat_activity
WHERE state != 'idle'
  AND query_start < now() - interval '30 seconds'
ORDER BY duration DESC;
```

2. Найти цепочку блокировок:
```sql
SELECT blocked.pid AS blocked_pid, blocked_act.query AS blocked_query,
       blocking.pid AS blocking_pid, blocking_act.query AS blocking_query
FROM pg_locks blocked
JOIN pg_stat_activity blocked_act   ON blocked_act.pid = blocked.pid
JOIN pg_locks blocking ON blocking.locktype = blocked.locktype
  AND blocking.database     IS NOT DISTINCT FROM blocked.database
  AND blocking.relation     IS NOT DISTINCT FROM blocked.relation
  AND blocking.page         IS NOT DISTINCT FROM blocked.page
  AND blocking.tuple        IS NOT DISTINCT FROM blocked.tuple
  AND blocking.virtualxid   IS NOT DISTINCT FROM blocked.virtualxid
  AND blocking.transactionid IS NOT DISTINCT FROM blocked.transactionid
  AND blocking.classid      IS NOT DISTINCT FROM blocked.classid
  AND blocking.objid        IS NOT DISTINCT FROM blocked.objid
  AND blocking.objsubid     IS NOT DISTINCT FROM blocked.objsubid
  AND blocking.pid != blocked.pid
JOIN pg_stat_activity blocking_act  ON blocking_act.pid = blocking.pid
WHERE NOT blocked.granted AND blocking.granted;
```

3. Завершить блокирующий бэкенд:
```sql
SELECT pg_terminate_backend(<blocking_pid>);
```
