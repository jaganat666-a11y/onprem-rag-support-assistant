Растёт consumer lag в Kafka на топике payments. Как разобраться?

Эталон из набора

В runbook'ах этого нет (Kafka в корпусе не упоминается): правильный ответ — честно сказать об этом и не выдумывать шаги.

Ответ ассистента
В runbook'ах для разбора роста consumer lag в Kafka на топике payments нет прямого описания действий. Однако можно предложить следующие шаги, основанные на аналогичных процедурах из других runbook'ов:

1. **Проверить состояние и логи Kafka consumers:**
   ```bash
   docker ps --filter name=kafka-consumer
   docker logs kafka-consumer --tail=100 2>&1 | grep -E "error|lag|offset"
   ```

2. **Проверить метрики consumer lag в Grafana:**
   - Панель: `Kafka Consumers` → меры `consumer_lag` и `consumer_offset`.

3. **Проверить балансировку потребителей:**
   ```bash
   kafkacat -P -b <broker_address> -t payments
   ```

4. **Проверить состояние Kafka topics:**
   ```bash
   kubectl get pods -l app=kafka
   kubectl logs <kafka_pod_name> --tail=100 2>&1 | grep -E "topic|partition|replica"
   ```

5. **Проверить логи приложения, которое является consumer:**
   ```bash
   docker logs <app_container_name> --tail=100 2>&1 | grep -E "error|lag|offset"
   ```

6. **Проверить метрики в Prometheus:**
   ```bash
   curl -XGET http://<prometheus_url>/api/v1/query_range?query=consumer_lag&start=<timestamp>&end=<timestamp>&step=<step>
   ```

7. **Проверить состояние и логи Kafka brokers:**
   ```bash
   docker ps --filter name=kafka-broker
   docker logs kafka-broker --tail=100 2>&1 | grep -E "error|lag|offset"
   ```

Эти шаги помогут определить причину роста consumer lag и предпринять соответствующие меры. Опиранье ведется на основе общих практик и аналогий из других runbook'ов.

Комментарий судьи: После частичного признания отсутствия информации выдал изобретённые команды для Kafka (kafkacat, kubectl, docker ps kafka-consumer), которых нет в корпусе.

1. Проверьте живость контейнеров:
```bash
docker ps --filter "name=card-issuer" --filter "name=queue-worker"
```

2. Посмотрите хвост логов воркера:

```sql
SELECT status, COUNT(*) AS cnt, MIN(created_at) AS oldest
```

6. Если очередь застряла, временные меры:
   - Остановить повторные попытки:

q35 · судья: верно

Как найти в PostgreSQL запрос, который блокирует остальные?

Эталон из набора

RB-14: запрос к pg_locks с джойном к pg_stat_activity, где заблокированный NOT granted, а блокирующий granted, — выдаёт blocked_pid / blocking_pid и тексты запросов; долгие запросы — по pg_stat_activity с query_start старше 30 секунд.

Ответ ассистента
Для того чтобы найти запрос, который блокирует остальные, можно использовать следующий SQL-запрос:

```sql
SELECT blocked.pid AS blocked_pid, blocked_act.query AS blocked_query,
       blocking.pid AS blocking_pid, blocking_act.query AS blocking_query
FROM pg_locks blocked
JOIN pg_stat_activity blocked_act   ON blocked_act.pid = blocked.pid
JOIN pg_locks blocking ON blocking.locktype = blocked.locktype
  AND blocking.database     IS NOT DISTINCT FROM blocked.database
  AND blocking.relation     IS NOT DISTINCT FROM blocked.relation
  AND blocking.page         IS NOT DISTINCT FROM blocked.page
  AND blocking.tuple        IS NOT DISTINCT FROM blocked.tuple
  AND blocking.virtualxid   IS NOT DISTINCT FROM blocked.virtualxid
  AND blocking.transactionid IS NOT DISTINCT FROM blocked.transactionid
  AND blocking.classid      IS NOT DISTINCT FROM blocked.classid
  AND blocking.objid        IS NOT DISTINCT FROM blocked.objid
  AND blocking.objsubid     IS NOT DISTINCT FROM blocked.objsubid
  AND blocking.pid != blocked.pid
JOIN pg_stat_activity blocking_act  ON blocking_act.pid = blocking.pid
WHERE NOT blocked.granted AND blocking.granted;
```

Этот запрос показывает цепочку блокировок, где `blocked_query` — это запрос, который блокирует другие запросы, а `blocking_query` — это запрос, который ждет блокировки.

q36 · судья: верно

Диск на ноде забит, контейнеры в CrashLoop, no space left on device. Как быстро освободить место и не потерять данные?

Эталон из набора

RB-15: усечь самые тяжёлые docker-логи (truncate -s 0 по LogPath, не удалять), docker system prune -f без --volumes; тома postgres/loki не трогать — docker volume prune только после подтверждения L3 и резервной копии; затем перезапустить контейнеры и настроить ротацию логов.

Ответ ассистента
Для быстрого освобождения места на диске и сохранения данных можно выполнить следующие шаги:

1. **Усечь docker-логи:**
```bash
truncate -s 0 $(docker inspect --format='{{.LogPath}}' vllm_container)
truncate -s 0 $(docker inspect --format='{{.LogPath}}' loki)
```

2. **Удалить неиспользуемые docker-объекты:**
```bash
docker system prune -f
```

3. **Настроить ротацию логов:**
```yaml
logging:
  driver: "json-file"
  options:
    max-size: "50m"
    max-file: "5"
```

4. **Перезапустить контейнеры:**
```bash
docker compose up -d --force-recreate
```

5. **Проверить восстановление:**
```bash
curl -s http://localhost:8001/health | jq .
df -h /
```

q39 · судья: верно

A user paid via SBP, the money left their bank account, but the transaction has been stuck in PENDING for 20 minutes. What should the on-call engineer do?

Эталон из набора

RB-02: проверить laravel-worker и логи колбэка; взять sbp_operation_id из meta транзакции; запросить сверку у банка-партнёра; если списание подтверждено и card_credited_at IS NULL — довести вручную: php artisan sbp:finalize-transaction --txn=<txn_id> --force.

Ответ ассистента
На основе runbook'ов (RB-02, RB-06):

1. Получить `sbp_operation_id` из поля `meta` транзакции.
2. Запросить сверку у банка-партнёра через внутренний API или вручную через ЛК банка.
3. Если банк подтвердил списание и зачисление ещё не выполнено, вручную запустить доведение:
   ```bash
   docker exec laravel-app php artisan sbp:finalize-transaction --txn=tx_8f3ac1 --force
   ```
4. Проверить состояние транзакции:
   ```sql
   SELECT status, card_credited_at, converted_amount_usd FROM transactions WHERE id = 'tx_8f3ac1';
   ```

Если доведение не помогает или затронуто более 5 транзакций, эскалировать инцидент L3.

Действия основаны на RB-02 и RB-06.
