q02 · судья: частично

Эквайер иногда присылает одно и то же событие дважды. Как на уровне базы защититься от двойного зачисления?

Эталон из набора

RB-01: в webhook_events должно быть ограничение UNIQUE(event_id), а обработчик делает INSERT ... ON CONFLICT DO NOTHING до обновления баланса; если ограничения нет — миграция ALTER TABLE webhook_events ADD CONSTRAINT uq_event_id UNIQUE (event_id). Откат уже случившегося двойного зачисления — только через L3 с согласованием финансового контроля.

Ответ ассистента
Для защиты от двойного зачисления в базе данных можно добавить уникальное ограничение на столбец `event_id` в таблице `webhook_events`:

```sql
ALTER TABLE webhook_events ADD CONSTRAINT uq_event_id UNIQUE (event_id);
```

Также следует обеспечить, чтобы обработчик вставки делал `INSERT ... ON CONFLICT DO NOTHING`, чтобы игнорировать попытки вставить дубликаты `event_id`.

На основе runbook'ов ID: RB-01, RB-04.

Комментарий судьи: По сути верно (UNIQUE и ON CONFLICT), но ссылка на RB-04 лишняя.

q18 · судья: верно

Ночная сверка показала расхождение с банковским реестром на 23,52 ₽ по 4 транзакциям. Какие типичные причины?

Эталон из набора

RB-07: курс фиксируется на created_at, а банк считает по курсу на settlement_at (+5–30 мин); округление: PHP round($amount, 2) против банковского TRUNCATE(amount, 2).

Ответ ассистента
Типичные причины расхождения с банковским реестром могут быть:

1. Курс фиксируется на `created_at`, а банк считает по курсу `settlement_at` (+5–30 мин).
2. PHP `round($amount, 2)` против банковского `TRUNCATE(amount, 2)`.

q32 · судья: частично

В Grafana Explore нет свежих логов фасада, хотя Promtail вроде запущен. Что проверить и как починить?

Эталон из набора

RB-13: логи самого promtail (ошибка чтения positions-файла), готовность Loki (curl :3100/ready) и место на диске; содержимое /tmp/positions.yaml; самый частый фикс — остановить promtail, удалить битый positions-файл и запустить заново; при нехватке диска — retention или расширение тома.

Ответ ассистента
В данном случае можно следовать шагам из runbook'а RB-13 — Loki Not Ingesting Logs / Promtail Lag:

1. Проверить, что Promtail запущен и его логи:
```bash
docker ps --filter name=promtail
docker logs promtail --tail=100 2>&1 | grep -E "error|warn|lag|positions"
```

2. Проверить готовность Loki и давление на диск:
```bash
curl -s http://localhost:3100/ready
df -h /var/lib/docker/volumes/loki_data
```

3. Проверить Promtail positions файл:
```bash
docker exec promtail cat /tmp/positions.yaml
```

4. Проверить графики в Grafana:
- Панель `Loki / Chunks` → `Ingester: Log Entries Received Rate`
- LogQL для здоровья:
```logql
{job="facade"} |= "error" | json | line_format "{{.ts}} {{.msg}}"
```

5. Если логи не восстанавливаются, выполнить диагностику и попробовать исправления A или B.

Опираюсь на runbook'и RB-13 и RB-09.

Комментарий судьи: Диагностика есть, но нет самого фикса (удаление positions-файла), ссылка на RB-09 лишняя.

1. Завершить блокирующие процессы:
```sql
SELECT pg_terminate_backend(<blocking_pid>);
```

2. Перезапустить PgBouncer:

3. Проверить и настроить пулы соединений:
```bash
# Проверить текущие значения

SHOW pgbouncer.max_client_conn;
SHOW pgbouncer.default_pool_size;

# Проверить алерт в Grafana
```

4. Разобраться с long-running запросами и оптимизировать их.
