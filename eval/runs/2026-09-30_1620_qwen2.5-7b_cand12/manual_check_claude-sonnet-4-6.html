Растёт consumer lag в Kafka на топике payments. Как разобраться?

Эталон из набора

В runbook'ах этого нет (Kafka в корпусе не упоминается): правильный ответ — честно сказать об этом и не выдумывать шаги.

Ответ ассистента
В runbook'ах для решения проблемы роста consumer lag в Kafka на топике payments нет прямого описания действий. Однако можно предложить следующие шаги:

1. Проверить состояние consumers в Kafka:
   ```bash
   kafkacat -L -b <broker_address> -t payments
   ```

2. Проверить метрики consumer lag в Grafana:
   - Панель `Kafka Consumers` → график `consumer_lag` для топика `payments`.

3. Проверить логи消费者的拉高问题，可以参考以下步骤：

1. 检查Kafka消费者的状态：
   ```bash
   kafkacat -L -b <broker_address> -t payments
   ```

2. 在Grafana中检查消费者滞后的指标：
   - 仪表板 `Kafka Consumers` → 图表 `consumer_lag` 对于主题 `payments`。

3. 检查消费者日志：
   ```bash
   docker logs <consumer_container_name> -f
   ```

4. 检查Kafka Broker的日志：
   ```bash
   docker logs <broker_container_name> -f
   ```

5. 使用LogQL查询Loki中的相关日志：
   ```logql
   {job="kafka-consumer"} |= "lag" | json
   ```

6. 检查Kafka配置和资源使用情况：
   ```bash
   kafkacat -P -b <broker_address> -t payments
   ```

这些步骤可以帮助你诊断和解决Kafka消费者滞后的问题。请注意，具体的容器名称和地址需要根据实际情况进行替换。

q02 · судья: частично

Эквайер иногда присылает одно и то же событие дважды. Как на уровне базы защититься от двойного зачисления?

Эталон из набора

RB-01: в webhook_events должно быть ограничение UNIQUE(event_id), а обработчик делает INSERT ... ON CONFLICT DO NOTHING до обновления баланса; если ограничения нет — миграция ALTER TABLE webhook_events ADD CONSTRAINT uq_event_id UNIQUE (event_id). Откат уже случившегося двойного зачисления — только через L3 с согласованием финансового контроля.

Ответ ассистента
Для защиты от двойного зачисления в базе данных можно добавить уникальное ограничение на поле `event_id` в таблице `webhook_events`. Также следует использовать индекс уникальности для поля `idempotency_key`, если используется такой ключ для идемпотентности.

Вот как это можно сделать:

1. Добавить уникальное ограничение на поле `event_id`:
```sql
ALTER TABLE webhook_events ADD CONSTRAINT uq_event_id UNIQUE (event_id);
```

2. Добавить уникальный индекс для поля `idempotency_key` (если используется):
```sql
CREATE UNIQUE INDEX idx_idempotency_key ON webhook_events (idempotency_key);
```

Эти изменения помогут предотвратить двойное зачисление событий. Опираюсь на runbook с ID RB-01.

Комментарий судьи: Пропущено требование INSERT ... ON CONFLICT DO NOTHING до обновления баланса из RB-01.

q18 · судья: верно

Ночная сверка показала расхождение с банковским реестром на 23,52 ₽ по 4 транзакциям. Какие типичные причины?

Эталон из набора

RB-07: курс фиксируется на created_at, а банк считает по курсу на settlement_at (+5–30 мин); округление: PHP round($amount, 2) против банковского TRUNCATE(amount, 2).

Ответ ассистента
Типичные причины расхождения с банковским реестром могут быть связаны с различиями в моменте фиксации курса и методами округления. Конкретно:

1. Курс фиксируется на `created_at`, а банк считает по курсу `settlement_at` (+5–30 мин).
2. PHP `round($amount, 2)` против банковского `TRUNCATE(amount, 2)`.

По каким метрикам понять, что Promtail отстаёт от чтения файлов логов?

Эталон из набора

RB-13: promtail_read_bytes_total стоит на месте, а promtail_file_bytes_total продолжает расти — растущий разрыв значит, что Promtail не успевает читать.

Ответ ассистента

Это может свидетельствовать о проблеме с позиционным файлом или других блокирующих факторах.

q36 · судья: верно

Диск на ноде забит, контейнеры в CrashLoop, no space left on device. Как быстро освободить место и не потерять данные?

Эталон из набора

RB-15: усечь самые тяжёлые docker-логи (truncate -s 0 по LogPath, не удалять), docker system prune -f без --volumes; тома postgres/loki не трогать — docker volume prune только после подтверждения L3 и резервной копии; затем перезапустить контейнеры и настроить ротацию логов.

Ответ ассистента
Для быстрого освобождения места на диске и сохранения данных можно выполнить следующие шаги:

1. **Усечь логи тяжёлых контейнеров:**
```bash
truncate -s 0 $(docker inspect --format='{{.LogPath}}' vllm_container)
truncate -s 0 $(docker inspect --format='{{.LogPath}}' loki)
```

2. **Удалить неиспользуемые объекты:**
```bash
docker system prune -f
```

3. **Настроить ротацию логов:**
```yaml
logging:
  driver: "json-file"
  options:
    max-size: "50m"
    max-file: "5"
```

4. **Перезапустить контейнеры:**
```bash
docker compose up -d --force-recreate
docker ps -a  # убедиться, что все Up
```

5. **Проверить восстановление:**
```bash
curl -s http://localhost:8001/health | jq .
df -h /
```

q39 · судья: верно

A user paid via SBP, the money left their bank account, but the transaction has been stuck in PENDING for 20 minutes. What should the on-call engineer do?

Эталон из набора

RB-02: проверить laravel-worker и логи колбэка; взять sbp_operation_id из meta транзакции; запросить сверку у банка-партнёра; если списание подтверждено и card_credited_at IS NULL — довести вручную: php artisan sbp:finalize-transaction --txn=<txn_id> --force.

Ответ ассистента
На основе предоставленных runbook'ов, на-call инженер должен следовать следующим шагам:

1. **Получить `sbp_operation_id`** из поля `meta` транзакции.
2. **Запросить сверку у банка-партнёра** через внутренний API или вручную через ЛК банка; подтвердить статус операции по `sbp_operation_id`.
3. Если банк подтверждает успешное списание — **вручную запустить доведение**:
   ```bash
   docker exec laravel-app php artisan sbp:finalize-transaction --txn=tx_8f3ac1 --force
   ```
4. Убедиться, что автоконвертация и зачисление прошли:
   ```sql
   SELECT status, card_credited_at, converted_amount_usd FROM transactions WHERE id = 'tx_8f3ac1';
   ```
5. Если банк сообщает, что списание было, но доведение невозможно — перевести транзакцию в `FAILED` и инициировать возврат:
   ```bash
   docker exec laravel-app php artisan sbp:refund --txn=tx_8f3ac1
   ```
6. Если списания не было — перевести транзакцию в `FAILED` без возврата.
7. После стабилизации — зафиксировать инцидент в Яндекс Трекере и проверить очередь на наличие других зависших `PENDING`.

Опираюсь на следующие runbook'и: RB-02, RB-03, RB-06.
