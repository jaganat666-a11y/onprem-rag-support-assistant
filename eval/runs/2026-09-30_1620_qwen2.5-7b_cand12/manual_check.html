q17 · судья: частично

Секрет поменяли. Как безопасно переотправить вебхуки, которые упали за последние два часа?

Эталон из набора

RB-06: попросить эквайера переотправить или запустить php artisan webhooks:replay --since="2 hours ago" --status=failed; повтор должен быть идемпотентным — дедупликация по txn_id, переподтверждать только pending, терминальные пропускать.

Ответ ассистента
1. Идентифицируйте контейнер, который всё ещё использует старый секрет:
```bash
for c in webhook-handler payment-gateway; do
  echo "=== $c ==="; docker exec $c env | grep ACQUIRER_WEBHOOK_SECRET
done
```

2. Обновите секрет в нужном сервисе:
```bash
# Редактировать docker-compose.override.yml или .env, затем:
docker compose up -d --no-deps webhook-handler
```

3. Проверьте, что новый секрет активен:
```bash
docker exec webhook-handler env | grep ACQUIRER_WEBHOOK_SECRET
```

4. Попросите эквайера повторно отправить вебхуки для поражённого интервала времени:
```bash
docker exec laravel-backend php artisan webhooks:replay --since="2 hours ago" --status=failed
```

5. Мониторинг метрики `acquirer_webhook_401_rate` — она должна вернуться к нулю в течение 2 минут.

Ориентируюсь на runbook с ID RB-06 — Webhook Signature Mismatch After Secret Rotation.

Комментарий судьи: Нет требования идемпотентности повтора: дедуп по txn_id, переподтверждать только pending.

q19 · судья: верно

Как вытащить из базы транзакции, у которых сумма не совпадает с банковским реестром?

Эталон из набора

RB-07: JOIN transactions с bank_recon_import по b.bank_txn_ref = t.external_ref за вчерашнюю дату с условием ABS(t.amount_rub - b.bank_amount_rub) > 0.01, сортировка по величине дельты.

Ответ ассистента
Для выявления транзакций, у которых сумма в базе данных не совпадает с суммой из реестра банка, можно использовать следующий SQL-запрос:

```sql
SELECT
    t.id                         AS txn_id,
    t.user_id,
    t.amount_rub,
    t.amount_usd,
    t.fx_rate,
    t.created_at,
    b.bank_amount_rub,
    (t.amount_rub - b.bank_amount_rub) AS delta_rub
FROM transactions t
JOIN bank_recon_import b ON b.bank_txn_ref = t.external_ref
WHERE DATE(t.created_at) = CURRENT_DATE - 1
  AND ABS(t.amount_rub - b.bank_amount_rub) > 0.01
ORDER BY ABS(delta_rub) DESC
LIMIT 50;
```

Этот запрос сравнивает сумму транзакции в вашей базе данных (`t.amount_rub`) с суммой, указанной в реестре банка (`b.bank_amount_rub`). Если разница между этими суммами больше 0.01 рубля, то транзакция будет включена в результат. Результат сортируется по абсолютной величине дельты в убывающем порядке и ограничивается первыми 50 транзакциями.

Опираюсь на runbook с ID [RB-07 — Расхождение сверки — сумма в БД не совпадает с банковским реестром · Диагностика].

Какие метрики vLLM смотреть, если подозреваю переполнение KV-кэша?

Эталон из набора

RB-10: vllm:gpu_cache_usage_perc (близко к 100 %), vllm:num_preemptions_total (растёт), vllm:num_requests_waiting (очередь не рассасывается), p95 e2e latency по vllm:e2e_request_latency_seconds_bucket.

q35 · судья: частично

Как найти в PostgreSQL запрос, который блокирует остальные?

Эталон из набора

RB-14: запрос к pg_locks с джойном к pg_stat_activity, где заблокированный NOT granted, а блокирующий granted, — выдаёт blocked_pid / blocking_pid и тексты запросов; долгие запросы — по pg_stat_activity с query_start старше 30 секунд.

Ответ ассистента
Чтобы найти в PostgreSQL запрос, который блокирует остальные, можно использовать следующую команду:

```sql
SELECT blocked.pid AS blocked_pid, blocked_act.query AS blocked_query,
       blocking.pid AS blocking_pid, blocking_act.query AS blocking_query
FROM pg_locks blocked
JOIN pg_stat_activity blocked_act   ON blocked_act.pid = blocked.pid
JOIN pg_locks blocking ON blocking.locktype = blocked.locktype
  AND blocking.database     IS NOT DISTINCT FROM blocked.database
  AND blocking.relation     IS NOT DISTINCT FROM blocked.relation
  AND blocking.page         IS NOT DISTINCT FROM blocked.page
  AND blocking.tuple        IS NOT DISTINCT FROM blocked.tuple
  AND blocking.virtualxid   IS NOT DISTINCT FROM blocked.virtualxid
  AND blocking.transactionid IS NOT DISTINCT FROM blocked.transactionid
  AND blocking.classid      IS NOT DISTINCT FROM blocked.reclassid
  AND blocking.objid        IS NOT DISTINCT FROM blocked.objid
  AND blocking.objsubid     IS NOT DISTINCT FROM blocked.objsubid
  AND blocking.pid != blocked.pid
JOIN pg_stat_activity blocking_act  ON blocking_act.pid = blocking.pid
WHERE NOT blocked.granted AND blocking.granted;
```

Эта команда выведет информацию о блокирующих запросах и запросах, которые они блокируют. Опираюсь на runbook с ID RB-14.

Комментарий судьи: В SQL опечатка blocked.reclassid (такого столбца нет), запрос не выполнится.
